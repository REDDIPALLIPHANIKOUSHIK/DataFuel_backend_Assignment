# Code Review: `review_me.py`

This document provides a comprehensive engineering code review of `review_me.py`. The file was generated by an unassisted AI coding assistant and merged without review. Below are the most critical problems identified, ordered by severity.

---

### Issue 1: Mutable Default Argument in `fetch_inventory` (`results=[]`)
- **Problem:** The function definition `def fetch_inventory(store_id, as_of, cursor="0", results=[]):` uses a mutable list (`results=[]`) as a default argument.
- **Why it is wrong:** In Python, default parameter expressions are evaluated once when the function is defined, not each time the function is called. Every call that does not supply `results` shares the exact same list in memory.
- **Concrete Example:**
  In lines 71–72:
  ```python
  for sid in ["MUM-001", "MUM-002"]:
      save(conn, sid, fetch_inventory(sid, datetime.utcnow().isoformat()))
  ```
  When `fetch_inventory("MUM-001", ...)` executes, it populates `results` with MUM-001's 30 items. When `fetch_inventory("MUM-002", ...)` is called immediately afterwards, `results` still contains all 30 items from MUM-001! MUM-002's items are appended to that same list. Consequently, `save(conn, "MUM-002", ...)` inserts both MUM-001's and MUM-002's products under `MUM-002`.
- **Impact:** Critical cross-store data pollution and duplicate observations, invalidating all store and city OSA calculations.
- **Correct Solution:** Use `results: list | None = None` in the signature and initialize inside the function:
  ```python
  if results is None:
      results = []
  ```

### Issue 2: Infinite Retry Loop Without Bounds, Backoff, or 429 Handling
- **Problem:** `while True:` catches all exceptions (`except Exception:`) and unconditionally executes `time.sleep(0.1); continue` without a maximum retry limit or exponential backoff.
- **Why it is wrong:** If an error is non-transient (e.g., HTTP 400 Bad Request, HTTP 401 Unauthorized, or HTTP 404 Not Found), the loop will run infinitely, firing 10 requests every second. Additionally, upon hitting HTTP 429 (Rate Limit), it ignores the `Retry-After` header and hammers the server, quickly escalating into QuickMart's fair-use soft ban.
- **Concrete Example:**
  Line 72 passes `datetime.utcnow().isoformat()`, which outputs a naive ISO timestamp without timezone (e.g., `2026-10-02T10:30:00`). QuickMart's API strictly requires timezone-aware timestamps and returns HTTP 400 (`as_of must include a timezone`). `r.raise_for_status()` raises `HTTPError`, causing `fetch_inventory` to spin in an infinite 10 req/s loop forever. The script never completes.
- **Impact:** Infinite execution hangs, server flooding, and guaranteed rate-limit bans.
- **Correct Solution:** Enforce bounded retries (`max_retries=5`), parse the `Retry-After` header on HTTP 429, implement exponential backoff on 500/503, and fail immediately on 4xx client errors.

### Issue 3: SQL Injection Vulnerability and Syntax Errors via String Interpolation
- **Problem:** `save()` constructs SQL statements using Python f-strings:
  ```python
  conn.execute(
      f"INSERT INTO inventory VALUES ('{store_id}', '{it['sku_id']}', '{it['name']}', "
      f"{int(it['in_stock'])}, {it['qty']}, '{it['observed_at']}')"
  )
  ```
- **Why it is wrong:** Directly interpolating strings into SQL queries allows SQL injection and breaks on any string containing single quotes or apostrophes.
- **Concrete Example:**
  If a product name contains an apostrophe—such as `"Lay's Classic Salted 52g"` or `"Campbell's Soup"`—the resulting query is:
  `INSERT INTO inventory VALUES ('MUM-001', 'SKU-0012', 'Lay's Classic Salted 52g', ...)`
  SQLite encounters a syntax error (`near "s": syntax error`) and crashes the program.
- **Impact:** Immediate crash on common product names; severe security vulnerability.
- **Correct Solution:** Use parameterized queries:
  ```python
  conn.execute(
      "INSERT INTO inventory VALUES (?, ?, ?, ?, ?, ?)",
      (store_id, it['sku_id'], it['name'], int(it['in_stock']), it['qty'], it['observed_at'])
  )
  ```

### Issue 4: Missing Request Timeout
- **Problem:** `requests.get()` is invoked without a `timeout` argument.
- **Why it is wrong:** By default, Python `requests` has no timeout (`timeout=None`). If a network connection drops packets or the remote server delays response transmission (e.g., QuickMart intentionally delays requests by 8 seconds with 3% probability), the request may hang indefinitely.
- **Concrete Example:** A single dropped connection or slow upstream mock response stalls the scraper thread indefinitely without failing or retrying.
- **Impact:** Scrapers hang silently in production, blocking automated data pipelines.
- **Correct Solution:** Always pass an explicit timeout: `requests.get(..., timeout=15.0)`.

### Issue 5: Incorrect Availability Logic (`qty > 0` vs `in_stock`)
- **Problem:** In `city_osa()`, line 61 determines in-stock status by checking quantity:
  ```python
  in_stock = sum(1 for (qty,) in rows if qty > 0)
  ```
- **Why it is wrong:** The API specification explicitly designates `in_stock` (boolean) as the source of truth, noting that `qty` is purely informational. QuickMart has real-world cases of "ghost" inventory where `in_stock is True` but `qty == 0` (e.g., reserved stock).
- **Concrete Example:** If an item is in stock (`in_stock=True`, `qty=0`), `review_me.py` counts it as out of stock, incorrectly lowering the calculated OSA.
- **Impact:** Deflated and inaccurate availability metrics reported to brand clients.
- **Correct Solution:** Query and evaluate `in_stock == 1` directly from the database.

### Issue 6: Flawed OSA Calculation (Macro-averaging Store Percentages)
- **Problem:** `city_osa()` averages the per-store availability percentages:
  ```python
  per_store.append(in_stock / len(rows) if rows else 0.0)
  return round(100 * sum(per_store) / len(per_store), 2)
  ```
- **Why it is wrong:** This computes an unweighted macro-average rather than the true citywide OSA (`total in-stock observations / total observations`). Furthermore, if `stores` is empty, `len(per_store)` is 0, raising `ZeroDivisionError`.
- **Concrete Example:** Store A has 10 items, all 10 in stock (100%). Store B has 90 items, 45 in stock (50%). Total in-stock: 55 out of 100 observations = **55.0%** true OSA. Averaging store ratios yields `(100% + 50%) / 2 = 75.0%`, introducing an error of **+20.0 percentage points**.
- **Impact:** Misleading metrics that distort business reality and potential division-by-zero crashes.
- **Correct Solution:** Sum all in-stock observations across the city and divide by the total number of observations.

### Issue 7: Timezone Inconsistency and Naive Date Slicing
- **Problem:** Line 58 filters observations using `substr(observed_at, 1, 10) = ?`, and line 72 passes `datetime.utcnow().isoformat()`.
- **Why it is wrong:** String-slicing the first 10 characters assumes the stored timestamp matches the target IST day. However, QuickMart stores return timestamps with timezone offsets (Delhi in `+05:30`, Mumbai/BLR in `Z`). A UTC timestamp of `2026-09-27T19:00:00Z` falls on `2026-09-28` in IST (+05:30). Slicing the UTC string leaves it in `2026-09-27`, misallocating the data.
- **Impact:** Observations near midnight are assigned to the wrong calendar date.
- **Correct Solution:** Convert timestamps to IST before calendar date aggregation.

---

### Issue 8: Silent Ingestion of Partial Snapshots and Soft-Ban Edge Responses
- **Problem:** `fetch_inventory` completely ignores `body["partial"]` and `body["meta"]`.
- **Why it is wrong:** When QuickMart returns `partial: True` (such as DEL-004 on `2026-09-28T10:30:00Z`), the portal could not assemble complete data. Similarly, CDN "edge" responses indicate soft-ban degradation where items are truncated.
- **Impact:** Incomplete or degraded data is treated as valid, producing false availability metrics.
- **Correct Solution:** Detect `partial is True` and `meta.source == "edge"` and exclude or flag those sweeps as incomplete.
