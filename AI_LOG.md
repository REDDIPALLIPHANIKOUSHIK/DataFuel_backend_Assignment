# AI Interaction Log

This log documents the usage of AI coding assistance during the implementation of the DataFuel backend assignment, highlighting key prompts and genuine instances where AI suggestions required verification and correction.

---

## 1. AI Tools Used

- **Primary Assistant:** Antigravity AI Assistant (powered by Google DeepMind Advanced Agentic Coding / Gemini 3.8 Flash)
- **Role:** Architecture planning, rapid test scaffolding, reverse-engineering edge cases from `mock_portal.py`, reviewing `review_me.py`, and drafting comprehensive engineering documentation.

## 2. Key Prompts that Mattered

### Prompt 1: Identifying the Soft-Ban Mechanism
> *"Analyze mock_portal.py and API.md to identify the exact mechanism by which QuickMart degrades clients without returning HTTP errors, and how to forensically detect it."*
- **Outcome:** The analysis pinpointed line 191 in `mock_portal.py`, revealing that soft-banned responses return HTTP 200 with an empty or truncated items list, `next_cursor: None`, and `"meta": {"source": "edge"}` (in contrast to normal responses which return `"meta": {"source": "origin"}`). This allowed us to build an automated soft-ban detector and recovery mechanism.

### Prompt 2: Ensuring Micro-Aggregate OSA Rather Than Store Macro-Averaging
> *"Formulate the exact SQL query and logic for GET /osa such that citywide OSA is calculated as total in-stock observations across all complete sweeps divided by total observations, avoiding any store-level percentage averaging."*
- **Outcome:** Produced the SQL aggregation query joining `inventory_observations` through `store_sweeps` filtered by `status = 'complete'`, ensuring that product density variations across stores do not skew the business availability metric.

### Prompt 3: Timezone-Aware Midnight Boundary Handling
> *"Verify how UTC timestamps around the 18:30 UTC boundary map to IST calendar days and create dedicated unit test assertions for timestamps at 18:29:59Z, 18:30:00Z, and 19:00:00Z."*
- **Outcome:** Correctly mapped `2026-09-27T19:00:00Z` to IST calendar date `2026-09-28` (`00:30:00 IST`), preventing midnight data misallocation.

## 3. Real Instances Where the AI was Wrong & How It Was Caught

### Instance 1: Using Deprecated `@app.on_event("startup")`
- **What happened:** The initial FastAPI implementation generated by the AI used `@app.on_event("startup")` to initialize SQLite tables.
- **How it was caught:** When running `python -m pytest -v`, pytest emitted `DeprecationWarning: on_event is deprecated, use lifespan event handlers instead`.
- **Correction:** Refactored `app.py` to use FastAPI's modern `@asynccontextmanager` `lifespan` handler, eliminating all warnings.

### Instance 2: Inadvertent Removal of Helper Function During File Edit
- **What happened:** When replacing the FastAPI initialization block in `app.py` to add the lifespan handler, the AI's replacement chunk accidentally omitted the `get_yesterday_ist()` utility function.
- **How it was caught:** Immediately after the tool execution, the file contents were inspected using `view_file`. The missing function was detected before any runtime errors could occur.
- **Correction:** The `get_yesterday_ist()` function was promptly restored right above the endpoint definitions.

### Instance 3: Insufficient Retry Headroom for MUM-007 Under Compound 500/503 Failures
- **What happened:** The initial scraper implementation used `MAX_RETRIES = 5`. The AI assumed that since `MUM-007` returns HTTP 500 twice and succeeds on attempt 3, 5 retries would be sufficient. However, during the initial run of Sweep 1 (`2026-09-27T04:30:00Z`), random HTTP 503 errors coincided with the HTTP 500 errors, causing MUM-007 to reach attempt 5 and fail.
- **How it was caught:** The sweep summary printed `26 stores: 25 complete, 1 incomplete (MUM-007: HTTP 500: Exhausted maximum retry attempts)`.
- **Correction:** Increased `MAX_RETRIES = 6` in `sweep.py`. On the rerun, `MUM-007` absorbed the compound 500 and 503 errors and completed successfully, achieving 26 complete stores.
